# Context: Firebase

## Overview

A single Firebase project hosts the entire backend: Functions for the API, Firestore for storage, Hosting for the backoffice, and Authentication for backoffice access.

---

## Firestore Structure

```
projects/
  {projectId}/           ← document with project metadata (see below)
    schemas/
      {schemaVersion}    ← baked column definitions for a schema version
    sessions/
      {sessionId}        ← one document per session
```

The `{projectId}` is a UUID generated by the backoffice when a project is created. It matches `metaData.projectId` sent by the Unity SDK. The `{sessionId}` matches `metaData.sessionId` (UUID v4 generated by the Unity SDK).

**Project document shape** (`projects/{projectId}`):
```ts
{
  projectName: string;
  projectDescription: string;
  projectKey: string;   // secret for Unity SDK auth; immutable after creation
  createdAt: string;    // ISO 8601
  updatedAt: string;    // ISO 8601
}
```

**Schema document shape** (`projects/{projectId}/schemas/{schemaVersion}`):
```ts
{
  columns: Array<{
    columnName: string;           // e.g. "Tutorial Diegetico/Cliques/Botão A"
    dataType?: 'string' | 'number' | 'boolean' | null;  // for future display hints
  }>;
  bakedAt: string;  // ISO 8601 — when bakeSchema was last called for this version
}
```

See `docs/context/projects.md` for the full project management design.

Each session document contains the full `sessionData` object as submitted by Unity, stored as-is. No server-side transformation of the `data` array.

## Firebase Functions

Two HTTPS callable functions. TypeScript source in `functions/src/`.

### `submitSession`
- **Input:** `{ projectKey: string, sessionData: { metaData: {...}, data: [...] } }`
- **Auth:** Validates `projectKey` against `projects/{projectId}.projectKey` in Firestore
- **Behavior:**
  1. Validate required `metaData` fields (see `docs/context/session-data-format.md`)
  2. Validate `projectKey` against the project document (throws `permission-denied` on mismatch)
  3. Fetch `projects/{projectId}/schemas/{metaData.schemaVersion}` — if found, verify all schema `columnName` values are present in `sessionData.data` (throws `invalid-argument` listing missing columns if not)
  4. Write to `projects/{projectId}/sessions/{sessionId}` in Firestore
  5. Return `{ success: true }` or appropriate `HttpsError`

### `bakeSchema`
- **Input:** `{ projectId: string, projectKey: string, schemaVersion: string, columns: SchemaColumn[] }`
- **Auth:** Validates `projectKey` against `projects/{projectId}.projectKey` in Firestore
- **Behavior:**
  1. Validate required fields (`projectId`, `projectKey`, `schemaVersion`, non-empty `columns`)
  2. Validate `projectKey` against the project document
  3. Write to `projects/{projectId}/schemas/{schemaVersion}` with `{ columns, bakedAt }`
  4. Return `{ success: true }` or appropriate `HttpsError`

Unity calls `bakeSchema` from the Editor ("Bake Analytics" window) before the first session is submitted for a new schema version. Unity calls `submitSession` at runtime when a session ends.

## Firebase Hosting (Backoffice)

The Next.js backoffice is deployed to Firebase Hosting via static export (`next export`) or standard Next.js on Firebase. Configuration in `firebase.json` under the `hosting` key.

Build output from `backoffice/` is deployed to the default Firebase Hosting site.

---

## Authentication

Firebase Authentication is used for backoffice access. Internal team only for now — no self-signup. The auth structure (users scoped to projects) should be designed with future per-project access in mind, even if not implemented yet.

The Unity SDK does **not** use Firebase Auth. It authenticates requests to the Function via a project API key (a simple string secret configured in the SDK and validated by the Function).

## CI/CD — Firebase Deploy

`.github/workflows/firebase-deploy.yml` runs on push to `main`:
1. Install pnpm
2. `pnpm install` in `functions/` and `backoffice/`
3. Build `backoffice/` (`pnpm build`)
4. Build `functions/` (`pnpm build`)
5. Deploy with `firebase deploy` (uses `FIREBASE_TOKEN` secret)

Separate jobs for Functions and Hosting so they can fail independently.

## Local Development

Running `pnpm dev` from the repo root starts both Firebase Emulators and the Next.js dev server concurrently (see root `package.json`).

- Firebase Emulator UI: http://localhost:4000
- Next.js backoffice: http://localhost:3000
- Firestore emulator: localhost:8080
- Auth emulator: localhost:9099
- Functions emulator: localhost:5001

The backoffice connects to emulators when `NEXT_PUBLIC_USE_EMULATOR=true` is set in `backoffice/.env.local`. Copy `backoffice/.env.local.example` to get started.

The Firebase Emulators accept `demo-*` project IDs (e.g., `demo-cre-analytics`) without requiring a real Firebase project.

## firebase.json

Manages:
- `functions` — source at `functions/`, runtime `nodejs20`
- `hosting` — public directory from `backoffice/out` (or `.next` depending on export strategy)
- `firestore` — rules file at `firestore.rules`

Emulator ports:
- Functions: 5001
- Firestore: 8080
- Hosting: 5000
