# Context: Firebase

## Overview

A single Firebase project hosts the entire backend: Functions for the API, Firestore for storage, Hosting for the backoffice, and Authentication for backoffice access.

---

## Firestore Structure

```
projects/
  {projectId}/
    sessions/
      {sessionId}        ← one document per session
```

The `{projectId}` matches the `projectId` field in `metaData`. The `{sessionId}` matches `metaData.sessionId` (UUID v4 generated by the Unity SDK).

Each session document contains the full `sessionData` object as submitted by Unity, stored as-is. No server-side transformation of the `data` array.

---

## Firebase Functions

Single function: `submitSession`

- **Trigger:** HTTPS callable (or HTTP POST — decide at implementation time)
- **Path:** `/submitSession`
- **Auth:** Requires a valid project API key (passed as a header or in the request body — define at implementation time)
- **Input:** `{ sessionData: { metaData: {...}, data: [...] } }`
- **Behavior:**
  1. Validate required `metaData` fields (see `docs/context/session-data-format.md`)
  2. Write to `projects/{projectId}/sessions/{sessionId}` in Firestore
  3. Return `200 OK` with `{ success: true }` or appropriate error

Functions are written in TypeScript. Source in `functions/src/`.

---

## Firebase Hosting (Backoffice)

The Next.js backoffice is deployed to Firebase Hosting via static export (`next export`) or standard Next.js on Firebase. Configuration in `firebase.json` under the `hosting` key.

Build output from `backoffice/` is deployed to the default Firebase Hosting site.

---

## Authentication

Firebase Authentication is used for backoffice access. Internal team only for now — no self-signup. The auth structure (users scoped to projects) should be designed with future per-project access in mind, even if not implemented yet.

The Unity SDK does **not** use Firebase Auth. It authenticates requests to the Function via a project API key (a simple string secret configured in the SDK and validated by the Function).

---

## CI/CD — Firebase Deploy

`.github/workflows/firebase-deploy.yml` runs on push to `main`:
1. Install pnpm
2. `pnpm install` in `functions/` and `backoffice/`
3. Build `backoffice/` (`pnpm build`)
4. Build `functions/` (`pnpm build`)
5. Deploy with `firebase deploy` (uses `FIREBASE_TOKEN` secret)

Separate jobs for Functions and Hosting so they can fail independently.

---

## Local Development

- `firebase emulators:start` — runs Functions and Firestore locally
- The backoffice can point to the local emulator via environment variables
- The Unity SDK's endpoint URL is configurable — point to emulator during development

---

## firebase.json

Manages:
- `functions` — source at `functions/`, runtime `nodejs20`
- `hosting` — public directory from `backoffice/out` (or `.next` depending on export strategy)
- `firestore` — rules file at `firestore.rules`

Emulator ports:
- Functions: 5001
- Firestore: 8080
- Hosting: 5000
